# SQLite ALTER TABLE 规范与 12 步表重构模式文档

## Summary

本源文档是 SQLite 官方关于 `ALTER TABLE` 语法限制、内部实现原理以及复杂 Schema
变更操作（Section 8: Making Other Kinds Of Table Schema
Changes）的权威规范指南。SQLite 原生直接支持的修改仅限于重命名表（RENAME
TO）、重命名列（RENAME COLUMN）、添加列（ADD COLUMN）以及删除列（DROP
COLUMN）。对于添加或修改约束（如 CHECK
约束、外键约束、主键修改、列类型变更以及列重排序等），SQLite 并不支持通用的
`ALTER TABLE ... ADD CONSTRAINT` 语句，必须通过标准的 12 步表重构（Table
Recreation）流程完成。

文档系统性地拆解了 12 步标准规程的核心要点：必须在事务外部执行
`PRAGMA foreign_keys = OFF;` 禁用外键检查（在多语句事务内部执行此 PRAGMA
是无效的 no-op）；在事务内构建带有完整目标结构的新表 `new_X`，通过
`INSERT INTO new_X SELECT ... FROM X` 迁移存量数据，删除旧表 `X`，重命名 `new_X`
为 `X`，并重新创建相关的索引、视图与触发器；在事务提交前调用
`PRAGMA foreign_key_check`
严格核实引用完整性未受破坏，提交事务后再重新启用外键约束。文档还对比了错误的反向重命名流程（先重命名旧表），指出该做法会导致触发器、视图与外键引用被破坏。在
[[entities/searcher-项目]] 的数据层 [[entities/drizzle-sqlite-store]] 中，向
`webapp_groups` 添加 `folder_size` 及其枚举 CHECK 约束的迁移（如
`drizzle/0010_brainy_nemesis.sql`）正是这一标准模式的落地实践（参见
[[concepts/sqlite-table-recreation-migration]] 与
[[sources/sqlite-table-recreation-migration-zero-loss]]），且通过了零数据丢失自动化回归测试。

## Key Takeaways

1. **事务外管理外键开关**：`PRAGMA foreign_keys = OFF;`
   必须在独立非事务态执行；如果在 `BEGIN TRANSACTION` 内部执行，SQLite
   不报错但该命令完全静默无效。
2. **标准表重建四步核心**：创建目标临时表 `__new_X` →
   `INSERT INTO __new_X SELECT ... FROM X` 复制存量数据 → `DROP TABLE X`
   删除旧表 → `ALTER TABLE __new_X RENAME TO X`
   还原表名。这一顺序能确保视图、外键和触发器引用不会被提早篡改损坏。
3. **引用完整性闭环核验**：在事务提交前必须执行
   `PRAGMA foreign_key_check`，以确定所有子表（例如
   `webapps.group_id`）的外键关联完全有效、无悬挂孤儿外键引用。
