# Receiving Shared Data with the Web Share Target API
> _Original: [https://developer.chrome.com/docs/capabilities/web-apis/web-share-target](https://developer.chrome.com/docs/capabilities/web-apis/web-share-target)_

## Summary

Chrome for Developers 关于 Web Share Target 的指南。已安装（满足 installability 且已添加到主屏幕）的 PWA 可通过 manifest 的 `share_target` 成员出现在系统分享面板中；安装前置条件防止站点擅自注册为分享目标。每个 manifest 只能有一个 `share_target`，需要分流时应在落地页内提供选项。

三类场景：只接收 `title`/`text`/`url` 时用 `GET`（`enctype` 固定为 `application/x-www-form-urlencoded`，其他值被忽略），浏览器在新窗口打开 `action` 并附带 query string，页面用 `URLSearchParams` 解析；会修改应用状态（如保存书签）时用 `POST` + `multipart/form-data`；接收文件时必须 `POST` + `multipart/form-data` 并声明 `files`（`name` + `accept`，建议 MIME 与扩展名同时给出）。`POST` 分享通常由 service worker 的 `fetch` 处理。文档建议用 service worker 预缓存 `action` 页以支持离线打开。

## Key Takeaways

- 各发送方提供的字段不一致（有的只给 `text` 且内含 URL），落地页需自行归一化 title/text/url。
- Searcher 选择 `GET /share`（`web/public/manifest.webmanifest`），契约测试 `web/src/pwa/manifest.test.ts` 的理由是：POST 目标会绕过 API 的 Origin 检查。分享内容由前端落地页转为一条笔记；未登录时内容只保留在当前标签页，登录后再写入。
- `GET` 分享意味着分享内容出现在 URL 中，落地页应在消费后替换地址。Searcher `SharePage` 三条分支均 `navigate(..., { replace: true })`：无内容回首页；未登录时 `stashSharedNote` 暂存后跳转登录（`search` 清空）；已登录时经 router state 交给首页记录，`/share?...` 不留在历史中。
