# File Attachments
> _Original: [https://www.assistant-ui.com/docs/guides/attachments.md](https://www.assistant-ui.com/docs/guides/attachments.md)_

## Summary

文档阐述了 `@assistant-ui/react` 的附件系统架构，由三层组成：处理文件生命周期的 `AttachmentAdapter`、渲染预览/状态的 UI Primitives（如 `AttachmentPrimitive`），以及跨运行时（`useChatRuntime`、`useLocalRuntime`、`useExternalStoreRuntime` 等）的集成机制。除了内置的 `SimpleImageAttachmentAdapter`、`SimpleTextAttachmentAdapter` 与 `CompositeAttachmentAdapter` 外，自定义适配器需实现 `accept`、`add`、`send` 与 `remove` 四个成员。

在交互生命周期上，`add({ file })` 可返回 `PendingAttachment` 或作为 async generator 逐次 yield 同 `id` 的进度状态；而在上传尚未完成时允许直接点击发送，消息会先进入 `composer.submission` 再经 `composer.inTransit` 过渡到线程消息，但必须等待所有附件完成 `send()` 后才真正送入 Runtime。`send(attachment, { signal })` 接收 `AbortSignal`，当发送被取消或线程被销毁时触发中止。

针对校验与失败处理，官方明确了 `composer.attachmentAddError` 事件的三类 `reason`：`no-adapter`、`not-accepted`（按 `accept` 校验 MIME 或扩展名）和 `adapter-error`（`add()` 抛出异常或返回 `status.reason === "error"`）。同时指出外部来源附件（传入 `CreateAttachment` 描述符）绕过 `add()` 上传步骤，但仍受 `adapter.accept` 约束。

## Key Takeaways

- **`AttachmentAdapter` 四步契约**：`accept` 过滤类型，`add` 生成或流式更新 `PendingAttachment`（常见终态 `requires-action` / `composer-send`），`send` 在发送时将其转为 `CompleteAttachment`（并响应 `AbortSignal`），`remove` 负责移除清理。
- **失败回滚语义**：当消息发送失败或被取消时，文本与附件会退回 composer（先于之后新输入的内容），失败项标记 `status: { type: "incomplete", reason: "error" }`。
- **错误观测通道**：`useAuiEvent("composer.attachmentAddError", ...)` 可统一捕获 `no-adapter`、`not-accepted` 与 `adapter-error`；对于 `adapter-error`，若在失败前已产生附件实例则携带 `attachmentId`。
- **外部附件与大文件模式**：小图可转 base64 data URL，大文件应上传对象存储并在 `content` 中传递 URL 引用。
