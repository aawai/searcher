# The Service Worker Lifecycle (web.dev)
> _Original: [https://web.dev/articles/service-worker-lifecycle](https://web.dev/articles/service-worker-lifecycle)_

## Summary

Jake Archibald 关于 service worker 生命周期的权威说明。生命周期的设计目标：让 offline-first 成为可能；新 worker 可以在不干扰当前 worker 的情况下就绪；同一页面整个生命期内只被同一个 worker（或无 worker）控制；**同一时刻只运行站点的一个版本**，避免多个标签页对共享存储持不同假设而导致数据损坏。

状态序列为 download/parse → `install`（`event.waitUntil()` 决定成败，失败即丢弃）→ `waiting`（直到旧 worker 控制的 client 数为 0；刷新时新旧页面重叠，单次刷新不足以切换）→ `activate`（清理旧缓存、迁移数据的时机，`waitUntil` 会缓冲 fetch 等功能事件）。`clients.claim()` 让已激活 worker 接管未受控页面；`self.skipWaiting()` 跳过 waiting，但会让新 worker 接管由旧版本加载的页面，可能破坏一致性。

更新检查发生于作用域内导航、功能事件（24h 内未检查过）或 `reg.update()`；字节不同即视为新版本。Chrome 68+ 默认忽略 SW 脚本的 HTTP 缓存头（可用 `updateViaCache` 调整）。不要给 SW 脚本换 URL：旧 SW 缓存的 `index.html` 会一直注册旧 URL，导致永远无法更新。

## Key Takeaways

- 推荐模式：新版本在 `install` 中写入**带版本名的缓存**（如 `myapp-static-v2`），在 `activate` 中删除不在预期列表内的缓存；同源多站点需用前缀隔离缓存名。
- `skipWaiting()` 适合由用户交互触发（页面 `postMessage` → SW 调用），而非无条件写在 `install` 里。
- 整个更新周期可观察：`reg.installing`/`reg.waiting`/`updatefound`/`statechange`/`controllerchange`，足以实现"新版本已就绪 · 刷新"提示。
- Searcher 的实现与此一致：`web/src/pwa/sw.ts` 在 `install` 校验 shell 资产属于同一构建后预缓存，`activate` 删除过期 shell 缓存并 `clients.claim()`，仅在收到 `{type: "activate"}` 消息时 `skipWaiting()`；注册使用 `updateViaCache: "none"`。
